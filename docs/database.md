# Database Standards

## Engine

PostgreSQL **18**. The same major version is used everywhere:
- local development: `postgres:18` in `docker-compose.yml`, published on host port 5433
- tests: `postgres:18` through Testcontainers, in `TestcontainersConfiguration`
- production

No other database engine is used anywhere, including in tests.

## Naming

| Object | Convention | Example |
|---|---|---|
| Table | snake_case, plural | `contact_messages`, `refresh_tokens` |
| Column | snake_case | `google_subject` |
| Primary key column | `id` | `id` |
| Foreign key column | `<singular referenced table>_id` | `user_id` |
| Join table | both table names, alphabetical | `projects_users` |
| Primary key constraint | `pk_<table>` | `pk_contact_messages` |
| Foreign key constraint | `fk_<table>_<column>` | `fk_contact_messages_user_id` |
| Unique constraint or index | `uq_<table>_<columns>` | `uq_users_google_subject` |
| Index | `ix_<table>_<columns>` | `ix_contact_messages_status_created_at` |
| Check constraint | `ck_<table>_<rule>` | `ck_contact_messages_status` |

## Keys

- **Primary keys:** `id uuid`, generated by the application as UUID version 7. Version 7 is
  time-ordered, which keeps indexes efficient.
- **Foreign keys:**
  - Always declared as constraints.
  - `ON DELETE` is always explicit: `RESTRICT` by default, `CASCADE` only for children that can't
    exist without their parent.
- **Composite primary keys** appear only in join tables.

## Columns and types

| Kind | Rule |
|---|---|
| Nullability | `NOT NULL` by default. A column is nullable only when absence means something. |
| Timestamps | `timestamptz`, always in UTC. Every table has `created_at timestamptz NOT NULL` and `updated_at timestamptz NOT NULL`. |
| Text | `varchar(n)`, where `n` matches the contract's `maxLength`. Use `text` when the contract sets no limit. |
| Enums | `varchar` plus a `CHECK` constraint, not a PostgreSQL `enum` type, which is harder to change. |
| Booleans | `NOT NULL` with a default, named `is_*` or `has_*`. |
| Optimistic locking | Tables whose rows are changed through the API have `version bigint NOT NULL DEFAULT 0`. |

## Constraints and indexes

- Business uniqueness is enforced by a unique constraint or a unique index, not only in code. For
  example, `uq_users_google_subject`. `users.email` is intentionally not unique, because identity
  is the Google subject ([ADR-006](decisions/006-google-sign-in.md)).
- Every foreign key column is indexed.
- Columns used in list filters or sorting are indexed.
- A migration comment explains why each non-obvious index exists.
- No speculative indexes.

## Deletion

Rows are deleted with a hard delete. **Soft delete is not used by default.**

Why: soft delete forces every query and every unique constraint to exclude deleted rows, and missing
that filter even once leaks data. A table that genuinely needs history or undo gets an ADR and its
own design, such as an `archived_at` column or a history table.

## Transactions

- **Boundary:** a transaction starts and ends at a service method. One use case is one transaction.
- **Keep them short:** no network calls, file I/O or external APIs inside a transaction.
- **Queries** run in read-only transactions.
- **Isolation:** `READ COMMITTED` by default. Concurrent updates are detected with optimistic
  locking (`version`) and return 409.

## Migrations

- **Tool:** Flyway, forward-only ([ADR-004](decisions/004-database-migration.md)).
- **File names:** `V{n}__{snake_description}.sql`, for example `V2__create_contact_messages.sql`. `n` is the
  next integer in sequence.
- **An applied migration is never edited, reordered or deleted.** A mistake is fixed with a new
  migration.
- **One logical change per migration.** Schema changes and data changes go in separate migrations.
- **The application only validates the schema, never generates it:** `ddl-auto=validate`.
- **Destructive changes happen in two releases.** First stop using the column or table, then drop it
  in a later release.
- **Location:** `backend/spring-boot/src/main/resources/db/migration/`.
- **Development seed data:** a separate Flyway location that only the `local` profile enables. Seed
  data is never part of the versioned schema migrations.

When the second backend implementation starts, an ADR decides whether alternative backends share
these migrations or keep their own equivalent ones.
